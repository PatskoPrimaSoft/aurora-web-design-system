# Использование в Angular-приложении

Дизайн-система и Angular UI kit устанавливаются одним пакетом
`@primasoftllc/design-system`. CSS, токены, шрифты и Angular-компоненты согласованы
по версии; отдельный пакет `ng-ui-kit` и React-зависимости для Angular не нужны.

Проверенные потребители — Angular 19.2.25 и 20.3.34 с Zone.js.

Правила компонентов и критерии совместимости описаны в [правилах UI kit](../../ng-ui-kit/docs/development.md).

## 1. Доступ к пакету

Репозиторий `PrimaSoftLLC/aurora-web-design-system` публичный: для чтения
исходников отдельный доступ не нужен. Пакет `@primasoftllc/design-system`
распространяется через GitHub Packages.

Для установки npm-пакетов GitHub Packages требует авторизацию даже при публичной
видимости пакета. Публичность исходников и права на пакет — разные настройки;
подробнее — [документация GitHub Packages](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-npm-registry#authenticating-to-github-packages).

1. Создайте PAT **classic** со scope `read:packages` (GitHub → Settings → Developer settings → Personal access
   tokens → Tokens (classic)). Fine-grained токен GitHub Packages не принимает.
2. Положите токен в переменную окружения `NODE_AUTH_TOKEN` (в профиль оболочки, не в репозиторий).

## 2. `.npmrc` в корне приложения

```
@primasoftllc:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
```

Файл коммитится: токена в нём нет, только ссылка на переменную.

## 3. Установка

```bash
npm i -E @primasoftllc/design-system # точная версия, без ^: обновление — отдельный коммит
npm i -D stylelint postcss-scss      # линтер (шаг 8)
```

Базовый Angular-вход не требует ECharts. Устанавливайте `echarts` отдельно, если используете графики.
Выбирайте выпущенную версию, в которой уже есть нужный Angular-компонент:
наличие компонента в ветке разработки не означает его наличие в реестре.

## 4. Стили: `angular.json`

В `projects.<app>.architect.build.options` добавьте или обновите свойство `styles`.
CSS пакета должен идти перед стилями приложения:

```json
{
  "styles": [
    "node_modules/@primasoftllc/design-system/dist/styles.css",
    "src/styles.scss"
  ]
}
```

Шрифты (Inter Tight, JetBrains Mono) и иконки Material Symbols подключаются самим `styles.css` — в `assets`
ничего добавлять не нужно, в Google Fonts интерфейс не ходит.

## 5. Публичные входы пакета

Пакет содержит скомпилированную Angular-библиотеку с типами. Для нового проекта
алиас в `tsconfig.paths` не нужен. Используйте публичные входы:

| Импорт от `@primasoftllc/design-system` | Что подключает |
|---|---|
| `/angular` | `provideAurora`, `AuroraThemeService`, `AuroraScopeDirective`, `DsButtonComponent` и их типы |
| `/angular/echarts` | Angular-интеграция графиков; требует отдельной установки ECharts |
| `/styles.css` | Общие стили, токены, шрифты и иконки; физический путь для `angular.json` показан выше |
| `/tokens.css`, `/tokens.json` | Отдельные CSS-токены и JSON-справочник; для обычного UI kit достаточно `styles.css` |
| `/stylelint-config` | Конфиг линтера для CSS/SCSS приложения |
| `/echarts-theme` | Самостоятельный JavaScript-мост токенов к ECharts |
| Корень пакета | React-компоненты; Angular-приложение использует `/angular` |

Каталоги `design-system/` и `ng-ui-kit/` разделяют исходники в этом репозитории,
но не меняют npm-импорты. `.tmp/package/` — внутренняя директория подготовки
поставки: копировать её файлы в приложение или ссылаться на неё из `tsconfig` не нужно.
Прежние исходные TypeScript-адаптеры оставлены только для
[миграции существующих алиасов](#переход-со-старого-алиаса).

## 6. Тема, оформление, плотность

`app.config.ts`:

```ts
import {ApplicationConfig} from '@angular/core';
import {provideAurora} from '@primasoftllc/design-system/angular';

export const appConfig: ApplicationConfig = {
  providers: [...provideAurora({theme: 'DEFAULT'})],
};
```

Передайте `appConfig` вторым аргументом `bootstrapApplication` в `src/main.ts`:

```ts
import {bootstrapApplication} from '@angular/platform-browser';
import {AppComponent} from './app/app.component';
import {appConfig} from './app/app.config';

bootstrapApplication(AppComponent, appConfig).catch(console.error);
```

Пути соответствуют приложению с `src/app/app.component.ts` и
`src/app/app.config.ts`; при другой структуре измените только относительные импорты.
Провайдер запускает сервис при bootstrap и выставляет атрибуты на `<body>`.
Для переключателей оформления или плотности внедряйте `AuroraThemeService`
в компонент через `inject(AuroraThemeService)`; доступны `appearance()`,
`density()`, `setAppearance('dark')`, `setDensity('compact')` и `setTheme('RED2')`.

`src/index.html` — те же значения статически, чтобы до старта Angular страница не мигнула без темы:

```html
<body data-ds-theme="DEFAULT" data-ds-appearance="light" data-ds-density="cozy">
```

Сервис держит на `<body>` три атрибута: `data-ds-theme` (`DEFAULT` | `RED2`), `data-ds-appearance`
(`light` | `dark`), `data-ds-density` (`cozy` | `compact`). Оформление и плотность он запоминает в
`localStorage`, тему — нет: это свойство тенанта. Пользователю дайте переключатели оформления и плотности, обе
плотности обязательны.

Корректные значения в storage имеют приоритет над конфигурацией; при недоступном
storage используются значения конфигурации. `FRONT_BRAND` и классы `theme-*` можно
сохранить: сервис меняет только `data-ds-*`. Передавайте бренд в `provideAurora({theme})`,
после загрузки конфигурации — в `AuroraThemeService.setTheme(theme)`.

Переопределить скоуп на части страницы — [директива или атрибут на обёртке](#локальные-скоупы):

```html
<section auroraScope density="compact">…</section>
<div data-ds-appearance="dark">…</div>
```

## 9. Как писать стили

- Цвет — только `var(--ds-*)`. Размеры — только `px`, без `rem`.
- Свой `:focus`, рамку текстового поля и `box-shadow` не рисовать: кольцо фокуса и рамка уже в системе.
- Шрифт — ролью: `font: var(--ds-type-body)`.
- Литералы цветов в TypeScript (конфиги ECharts) линтер не видит — берите `dsEChartsTheme` из
  `@primasoftllc/design-system/echarts-theme` и перестраивайте график при смене скоупа (`auroraWatchScopes`,
  [графики](#echarts)).

Пример — [стили компонентов](#стили-компонентов).

## 10. Компоненты

Angular UI-компоненты разрабатываются централизованно в этом репозитории
и импортируются из `/angular` по [правилам UI kit](../../ng-ui-kit/docs/development.md).
Доступна [кнопка DsButtonComponent](../../ng-ui-kit/src/components/button/README.md):
добавьте её в `imports` standalone-компонента и используйте `<button dsButton>`.
Корневой импорт пакета уже поставляет скомпилированные React-компоненты.
Поддерживаются React / React DOM `^18.3.0 || ^19.3.1`; проверены 18.3.1 и 19.3.1.
Типы проверены с `@types/react` / `@types/react-dom` 18.3.31 / 18.3.7 и 19.3.0 / 19.3.0,
TypeScript 5.8.3, без `skipLibCheck`. Для React 19 проверены SSR/hydration, ref и события
полей, отправка формы, клавиатура select/tabs и диалог в портале потребителя в четырёх
сочетаниях бренда, оформления и плотности. `DsDialog` сам портал не создаёт.
В Next.js 15.5.28 проверены production-сборка, HTTP-маршрут и гидратация контролов:
импортируйте компоненты из клиентского компонента с `'use client'`.
React 19.0–19.2 и другие версии Next.js этой проверкой не покрыты.

Standalone-компоненты UI kit добавляются в `imports` каждого компонента,
чей шаблон их использует. Провайдер темы не регистрирует компоненты автоматически.
Полный пример кнопки приведён ниже; `loading` управляется приложением.

```ts
import {Component, signal} from '@angular/core';
import {DsButtonComponent} from '@primasoftllc/design-system/angular';

@Component({
  selector: 'app-save-example',
  standalone: true,
  imports: [DsButtonComponent],
  template: `<button dsButton icon="save" [loading]="saving()" (click)="save()">Сохранить</button>
    <p role="status">{{message()}}</p>`,
})
export class SaveExample {
  readonly saving = signal(false);
  readonly message = signal('');

  async save(): Promise<void> {
    this.saving.set(true);
    this.message.set('Сохраняем изменения…');
    try {
      // Демонстрация асинхронного действия; в приложении здесь вызов сервиса.
      await new Promise<void>(resolve => setTimeout(resolve, 500));
      this.message.set('Изменения сохранены.');
    } catch {
      this.message.set('Не удалось сохранить изменения. Попробуйте ещё раз.');
    } finally {
      this.saving.set(false);
    }
  }
}
```

Доступные inputs, тип кнопки и правила доступности — в [API кнопки](../../ng-ui-kit/src/components/button/README.md).

Карточки `design-system/components/Ds<Имя>/` описывают применение, вид и состояния; исходники
`design-system/components/src/components/**/Ds<Имя>.jsx` служат эталоном поведения.
Их `.d.ts` описывают React API, а не готовый Angular-контракт.
Для ещё не перенесённого компонента временная реализация в приложении должна
сохранять правила карточки. После появления библиотечного компонента используйте
его публичный импорт. Наличие React-карточки само по себе не означает наличие Angular-компонента.

Не хватило токена или компонента, спецификация не покрывает состояние — не изобретайте: `// TODO: DS-<n>` в коде
и задача в репозитории системы. Подробнее — [когда токена или компонента не хватает](#когда-токена-или-компонента-не-хватает).

## Локальные скоупы

Добавьте standalone-директиву `AuroraScopeDirective` из
`@primasoftllc/design-system/angular` в `imports` компонента.
Например, вместе с кнопкой: `imports: [DsButtonComponent, AuroraScopeDirective]`.
После этого в шаблоне доступны локальные скоупы:

```html
<section auroraScope density="compact">…</section>
<div data-ds-appearance="light">…</div>
```

Каждый атрибут переопределяет только свою ось. Компактная таблица наследует тему
и оформление страницы; светлая панель внутри тёмной страницы сохраняет плотность.
Не заданный input директивы удаляет локальный атрибут и возвращает наследование.

## ECharts

Установите ECharts только для приложений с графиками. Отдельный вход сохраняет
базовый Angular-пакет независимым от него:

```ts
import type {EChartsOption} from 'echarts/types/dist/echarts';
import {auroraChartChrome} from '@primasoftllc/design-system/angular/echarts';

export function chartOption(host: HTMLElement): EChartsOption {
  const chrome = auroraChartChrome(host);
  return {
    ...chrome,
    xAxis: {...chrome.xAxis, type: 'time'},
    series: [{type: 'line', data: [[Date.now(), 42]]}],
  };
}
```

Используйте собственные данные серии. Сохраняйте вложенные опции `chrome.xAxis`
и `chrome.yAxis`, когда добавляете тип оси, категории или пределы:

```ts
import {auroraWatchScopes} from '@primasoftllc/design-system/angular/echarts';

chart.setOption(chartOption(host), true);
const stop = auroraWatchScopes(host, () => chart.setOption(chartOption(host), true));
// В ngOnDestroy: stop(); chart.dispose();
```

Мост читает токены с реального DOM-узла. Наблюдение покрывает сам узел и цепочку
предков до `<html>`, включая промежуточную панель с локальным скоупом.
После изменения темы, оформления или плотности пересобирайте опции; при уничтожении
компонента обязательно вызывайте функцию отписки. Статическая зарегистрированная
JSON-тема не отслеживает смену атрибутов.

Самостоятельный JS-вход `/echarts-theme`, глобальный `dsEChartsTheme` и старые
TypeScript-адаптеры сохранены. Механический переход со старого алиаса описан
в [переходе со старого алиаса](#переход-со-старого-алиаса).

## Что проверяет линтер

| Правило | Что ловит |
|---|---|
| `aurora/known-token` | `var(--ds-…)` на несуществующий токен; объявление своих `--ds-*` |
| `aurora/no-literal-color` | hex, `rgb()`, `hsl()`, `oklch()`, именованные цвета |
| `aurora/no-rem` | `rem` вместо `px` |
| `aurora/focus-from-tokens` | свой `outline` / `box-shadow` в состоянии фокуса, `outline: none` |
| `aurora/shadow-token-only` | `box-shadow` мимо ступеней системы |
| `aurora/no-deprecated-token` | устаревшее имя-алиас (список `aliases` в `design-system/lint/naming.config.json`); предупреждение, не ошибка |

Версия правил совпадает с версией токенов: линтер поставляется в том же пакете.
Правила и опции — [справочник линтера](../lint/README.md). В новом приложении
включайте его сразу, в существующем — на срезе 1, после перевода цветов на токены.

### Ограничения

Литералы в TypeScript (конфиги ECharts — главный канал, через который цвета
просачиваются мимо SCSS), inline `[style]` в шаблонах Angular, глубокие импорты
внутренностей пакета. Это ESLint-слой, его пока нет.

И он ничего не знает про роль токена: `color: var(--ds-surface)` — формально
валидно, содержательно ошибка. Это видит только ревьюер, и ради этого приёмка
по-прежнему существует.

## Приёмка экрана

Шесть пунктов. Формулировки проверяемые — «выглядит как система» критерием не
является.

1. Ни одного литерального цвета вне токенов — ни в SCSS, ни в шаблоне, ни в TS.
2. Размеры в `px`. `rem` в новом коде нет (порталы ставят `html { font-size: 10px }`).
3. Собственных `:focus` и рамок полей нет — фокус и поле приходят из
   общего `dist/styles.css` пакета.
4. Тени — только ступенями системы (`var(--ds-shadow-*)`), своих `box-shadow` нет.
5. Экран отрисован в четырёх режимах и в каждом читается: DEFAULT/light/cozy,
   DEFAULT/dark/compact, RED2/light/cozy, RED2/dark/compact.
6. У каждой кнопки, которая шлёт запрос, есть состояние загрузки; AXE чистый;
   `:focus-visible` проверен с клавиатуры, а не в devtools.

### Передача на ревью

Заявка на приёмку — это ссылка на PR плюс четыре скриншота экрана в четырёх
режимах. Без скриншотов заявка не рассматривается: их отсутствие почти всегда
означает, что в тёмной теме экран не открывали.

Владелец смотрит: соответствие спецификации компонента, выбор токена по роли (не по
цвету), поведение в compact и в dark, пустое состояние и состояние загрузки.

CSS-нарушения должны быть исправлены до ревью. Литералы в TS, inline-стили и
глубокие импорты текущий stylelint не проверяет — их нужно смотреть отдельно.

Предметом приёмки не является вёрстка бизнес-логики, тексты и раскладка полей —
система задаёт внешний вид, а не структуру экрана.

## Ответственность

Подтверждённый первый потребитель пакета — aur-billing. Состояние пилотов и
готовность каждого приложения фиксируются в его задачах; этот документ не
объявляет внедрение завершённым. Найденные пробелы оформляются в репозитории
системы. Экран принимает владелец системы или назначенный ревьюер команды.

## Пилот

Пилот существует не чтобы «первое приложение выглядело хорошо», а чтобы вскрыть
дыры в системе до того, как в неё упрутся команды с легаси. Пилот обязан ответить
на список вопросов и закрыть каждый задачей в репозитории системы:

- каких токенов не хватило и в каких ролях;
- какие компоненты пришлось писать с нуля, потому что в системе нет спецификации;
- где спецификация есть, но она не покрывает реальное состояние (ошибка, загрузка,
  пусто, очень длинный текст, очень много колонок);
- что ломается в compact, что — в dark;
- что происходит с графиками при смене скоупа;
- что пришлось сделать вопреки правилам и почему.

Пока пилот идёт, каждое «сделаю пока по-своему» фиксируется как `// TODO: DS-<id>`
со ссылкой на задачу. Список этих TODO — и есть отчёт пилота.

**Пилот закрыт, когда:** все экраны приняты, список TODO пуст или сознательно
отложен владельцем, и правки, которые пилот породил, выпущены версией системы.
До этого момента существующие приложения не подключаются — иначе они получат
систему, которую придётся ломать мажором через месяц.

## Существующее приложение

Главное правило: **срез делается по всему приложению целиком, а не экран за
экраном**. «Три экрана полностью на системе, остальные как были» выглядит хуже,
чем приложение, которое вообще её не подключало, и команда быстро теряет к затее
интерес.

Порядок срезов — по возрастанию визуального риска:

**Срез 0 — подключение.** Пакет ставится, стили подключаются, но ничего своего не
удаляется. Вид приложения не меняется. Если меняется — значит есть конфликт
глобальных селекторов, и до его разбора дальше идти нельзя: скоуп вешается на
контейнер вместо `<body>`, пока легаси не вычищено.

**Срез 1 — цвета.** Литералы меняются на токены по таблице
[миграции](migration.md). Вид не меняется, дифф механический, делается массово
и ревьюится быстро. Здесь же включается линтер системы — с этого момента новые
литералы в проект не попадают.

**Срез 2 — типографика и плотность.** Вид меняется. Делается экраном за экраном и
согласуется до начала работ, а не после.

**Срез 3 — компоненты.** По одному, в порядке частоты: кнопка, поле, таблица,
диалог, дальше по месту. Каждый компонент — отдельный PR по всему приложению.

**Срез 4 — уборка.** Собственные `:focus`, тени, рамки, дубли переменных. Делается
последним, когда токены уже везде: раньше это просто сломает вид.

Не переписывается: бизнес-логика, структура экранов, роутинг. Если срез тянет за
собой рефакторинг логики — срез разбит неправильно.

## Когда токена или компонента не хватает

Локальный `#3A7BD5` «на время» — главный способ убить систему, и он всегда
появляется под дедлайном. Поэтому путь должен быть короче обхода:

1. Задача в репозиторий системы: что за роль, где именно, скриншот.
2. Сегодня, пока токена нет: ближайший подходящий токен по роли плюс
   `// TODO: DS-<id>`. Литерал не коммитится никогда.
3. Согласуйте срок ответа с владельцем в задаче. Общий SLA пока не установлен.

Отдельно: запрос «нам нужен свой цвет» почти всегда означает «нам нужна роль,
которой нет в системе». Обсуждается роль, а не hex.

## Антипаттерны

- Скопировать `tokens.css` к себе и «немного поправить».
- Форкнуть пакет под нужды одного приложения.
- Обернуть компонент системы в свою обёртку, которая переопределяет его стили.
- Принять экран, не открыв его в dark и compact.
- Переводить приложение без выбранного среза, критериев приёмки и задач на выявленные пробелы.
- Держать в приложении свой набор переменных, который «мапится» на токены.

## Обновление системы

`npm i -E @primasoftllc/design-system@X.Y.Z` отдельным коммитом. MAJOR — ломающие изменения: прочитайте раздел версии в
[CHANGELOG](../../CHANGELOG.md) и [карту миграции](migration.md), правки кода — в том же коммите.
Patch и minor не должны ломать приложение; major планируется отдельной задачей.
Приложение не остаётся на старом мажоре дольше одного релизного цикла системы.
Критерии выбора версии — [политика версий](../../docs/release.md#versioning).

## Переход со старого алиаса

Существующий алиас `/angular` на `components/src/templates/angular/index.ts` внутри пакета сохранён.
Старые адаптеры используют тот же сервис и InjectionToken, что и новые входы.
Для Angular application-builder старый исходный `index.ts` должен быть включён в `tsconfig.files`:

```json
{
  "files": ["node_modules/@primasoftllc/design-system/components/src/templates/angular/index.ts"]
}
```

Для перехода удалите только алиас `@primasoftllc/design-system/angular` из `paths`.
Импорты сервиса и директивы оставьте; `auroraChartChrome` и `auroraWatchScopes` перенесите
на `/angular/echarts`. Запись совместимого `index.ts` в `files` после перехода можно удалить.
CSS-путь, имена токенов и SCSS-партиал сохраняются.

## Если что-то не так

| Симптом | Причина |
|---|---|
| `npm i` — 401/403 от `npm.pkg.github.com` | проверьте `NODE_AUTH_TOKEN`, PAT classic со scope `read:packages` и права на пакет; публичность исходников не отменяет авторизацию npm |
| `npm i` — ERESOLVE по `echarts` или `stylelint` | проверьте диапазоны: echarts 6.1+, stylelint 16–17 |
| `Cannot find module 'echarts'` при сборке | установите ECharts при использовании `/angular/echarts` |
| Не найден `/angular` | проверьте установленную версию и оставшийся старый `paths` |
| Интерфейс в Helvetica, иконки — текстом | проверьте массив `styles` в `angular.json`, порядок CSS и загрузку шрифтов; путь — `node_modules/@primasoftllc/design-system/dist/styles.css` |
| Angular не распознаёт `dsButton`, `loading` или `auroraScope` | проверьте версию пакета и наличие `DsButtonComponent` / `AuroraScopeDirective` в `imports` компонента |
| Тема не меняется, на `<body>` нет `data-ds-*` | проверьте включение `...provideAurora(...)` в bootstrap-конфигурацию |
| CI: 403 на `npm ci` | репозиторию приложения не выдан доступ в настройках пакета (шаг 11) |
