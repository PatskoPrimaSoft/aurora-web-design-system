# aurora-web-design-system: правила для агентов

Пакет `@primasoftllc/design-system` в GitHub Packages. Репозиторий — источник
дизайн-системы: токены, компоненты, превью и документация редактируются здесь.
Утверждённая миграция: `docs/superpowers/plans/2026-10-02-repository-first.md`.

## Команды и разработка

- Node 22 из `mise.toml`: `mise exec -- npm …`.
- `npm test` — линтер, UI, поставка и release guard. `npm run verify` — полная проверка,
  включая CSS-каскад в браузере и tarball глазами потребителя.
- `npm run build` создаёт результаты в `dist/`; генерируемые файлы не правятся вручную.
  Каталог создаётся в `site/`; `npm run dev` открывает его на `127.0.0.1:5173`
  и обновляет страницы при правках, явно показывает ошибки сборки.
  Токены редактируются в `design-system/tokens/source.json`, компоненты — в `design-system/components/src`,
  примеры — в `design-system/components/*/preview.html`, общие стили — в `design-system/styles/`.
- Проверки дизайн-системы и фикстуры находятся в `design-system/tests/`, её
  инструменты — в `design-system/tools/`, правила линтера — в `design-system/lint/`.
  Корневые `tools/` и `tests/` содержат общую инфраструктуру сборки, поставки,
  CI/релиза и Pages. Совместимые публичные npm-пути генерируются в `.tmp/package/`.
  Упаковка — `npm run pack`; CI публикует `.tmp/package/` после verify без повторной сборки.
- CI делит verify на `components`, `catalogue`, `raster`, `angular` после общей
  сборки (`node tools/verify.mjs <group>`). Полный `npm run verify` сохраняет все
  проверки. Каталог — два worker, raster и Angular — по одному. После resize
  проверять геометрию iframe с ожиданием адаптации, не мгновенным измерением.
- Релизный CI может продвигать `verified-package` из успешного develop только
  при совпадении отпечатка исходников и проверке SHA/хешей файлов. Исключения —
  CHANGELOG и поля версии; изменение кода, тестов или workflow требует полного
  verify. При отсутствии артефакта CI выполняет весь набор; правила — docs/release.md.
- Сохранять публичные имена, пути, CSS-переменные и поведение. Для изменения props
  обновлять реализацию, `.d.ts` и метаданные карточки вместе.
- Цвета только через токены, размеры в px; внешние отступы задаёт родитель.
- Проверять DEFAULT/light/cozy, DEFAULT/dark/compact, RED2/light/cozy,
  RED2/dark/compact, клавиатуру и доступность затронутых примеров.
- В `CHANGELOG.md` добавлять изменения под `## [Unreleased]` для потребителя.

## Страницы компонентов

Для Angular UI kit применять [правила Angular-компонентов](ng-ui-kit/docs/development.md).
Сборка — Angular 19.2.25; tarball проверяется в потребителях Angular 19.2.25 и 20.3.34.
React API и React-превью не считать подтверждением Angular API и поведения.

Оформление `DsCheckbox` — обязательный стандарт для страниц всех компонентов.
При создании новой страницы и переработке существующей применять правила ниже
и [подробный стандарт](design-system/docs/component-pages.md). Основы, бренд, карта, миграционные
документы и эталонные экраны сохраняют собственную структуру.

### Структура и общая оболочка

- Подключать `layout="component"` в `@dsCard`; сохранять публичное имя, группу,
  aliases и назначение компонента в `subtitle`.
- Порядок: название и назначение → живые примеры → правила применения →
  пример кода → параметры → токены. Пустые блоки, дубли назначения, отдельные
  страницы описания/API и текстовые повторы показанных состояний не добавлять.
- Документация, заголовки и пояснения остаются на белой поверхности
  DEFAULT/light/cozy. Бренд, оформление и плотность меняют только демонстрации.
- Настройки находятся в хедере: компактные `DsMenu` с текущими значениями
  без видимых подписей «Бренд», «Оформление», «Плотность» и кнопка
  «Сравнить 4 режима». Доступные имена кнопок сохраняют назначение настройки.
  Строку вида `DEFAULT / light / cozy` у одиночного превью не выводить;
  в сравнении сохранять подписи для различения режимов.
- Одна колонка с общей левой границей и максимальной шириной 920 px.
  Типографику, интервалы и таблицы брать из `design-system/catalog/styles.css`, а оформление
  живых примеров — из `design-system/catalog/live-examples.css`; не дублировать их локально.

### Живые примеры, ссылки и код

- Использовать `body[data-ds-examples]`, `scopeMode="inherit"` и общие
  `LiveExamples` / `LiveExample` из `window.DsLiveExamples`.
  Эталон реализации — `design-system/components/DsCheckbox/preview.html`.
- Каждый самостоятельный сценарий — отдельный `LiveExample`: стабильный
  уникальный `id`, заголовок сценария, короткое полезное описание и работающая
  демонстрация в собственной области с тонкой рамкой. Описание можно опустить,
  если оно лишь повторяет заголовок. Не повторять название компонента и общий
  заголовок «Живые примеры» внутри превью.
- Начинать с обычного использования, затем показывать существенные сценарии
  и варианты. Матрица состояний при необходимости завершает набор.
  Интерактивные сценарии должны демонстрировать реальное поведение и состояние.
- Под каждым сценарием давать закрытый по умолчанию блок «Показать код».
  Сниппеты хранить в `design-system/components/<Name>/examples.json` по `id` примера и
  подключать через `script#example-code-sources[data-ds-example-sources]`.
  Код должен воспроизводить демонстрацию: импорты, начальное состояние,
  обработчики и необходимые вспомогательные компоненты.
- Использовать общие подсветку, копирование кода и кнопку ссылки возле
  заголовка. Не копировать обработчики темы, ссылок и буфера обмена в превью.
  Прямая ссылка сохраняет карточку, режим и якорь примера; при отказе буфера
  обмена общий шаблон обеспечивает ручное копирование.
- Оглавление содержит разделы страницы и вложенные заголовки живых примеров
  `h3[id]`; на широком экране закреплено справа, на узком раскрывается.
  В сравнении пункты не дублируются и ведут к первому превью.

### Документация и проверка переноса

- `README.md` содержит нужные правила применения и типичный пример кода;
  параметры генерируются из реализации и `.d.ts`, не копируются в Markdown.
  `API.md` объясняет роль токенов в компоненте. Заголовки и пояснения — по-русски.
- Превью адаптируется по ширине и высоте содержимого: без фиксированной высоты
  body, `100vh` и второй вертикальной прокрутки. Всплывающие слои не обрезаются;
  горизонтальная прокрутка допустима внутри широкого кода или таблицы.
- При переносе сохранять API и поведение компонента; менять представление
  документации и примеров. Проверять ширину 390 px и широкий экран, четыре
  режима из раздела «Команды и разработка», сравнение, клавиатуру, доступность,
  переходы оглавления, прямые ссылки и копирование кода.
- Проверять браузерный контракт `design-system/tests/browser/component-page.spec.js` и
  относящиеся к изменению проверки. Общие шаблоны исправлять централизованно,
  чтобы оформление всех страниц оставалось одинаковым.

## Страницы «Основ»

Применять при создании и переработке всех страниц раздела «Основы».
Ориентиры по подаче — «Типографика» и «Нейтральные цвета»; структура
страниц компонентов не обязательна для основ.

1. Начинать с применения: понятный пример интерфейса и задача, которую
   решает тема. Устройство токенов и технические параметры показывать позже.
2. Сразу объяснять, что система делает автоматически. Различать использование
   готовых компонентов и создание собственной разметки. Не создавать впечатление,
   что каждый заголовок, цвет или состояние нужно настраивать вручную.
3. Выстраивать материал от простого к сложному: пример интерфейса → краткая
   памятка выбора → практические сценарии → правила и типичные ошибки →
   технический справочник → пример кода и связанные темы. Ненужные разделы
   пропускать, не заполнять шаблон ради структуры.
4. Рекомендовать выбор по назначению. Объяснять подходящую роль для конкретной
   задачи. Исходные оттенки, размеры и другие примитивы показывать как устройство
   системы, а не основной способ оформления интерфейса.
5. Давать каждой теме одно место: памятка помогает выбрать, пример показывает
   результат, справочник уточняет параметры. Не повторять одинаковые объяснения
   в этих блоках и под кодом.
6. Скрывать необязательные подробности: длинные шкалы, полные наборы значений
   и редкие варианты раскрывать по запросу. Основные правила и существенные
   ограничения оставлять видимыми.
7. Показывать реальные сценарии и готовые компоненты там, где речь об их
   применении. Интерактивные примеры должны работать. Сравнения «рекомендуется /
   избегайте» должны показывать одну конкретную разницу.
8. Писать простым языком и точно: сначала знакомое понятие, затем технический
   термин, например «межбуквенный интервал (трекинг)». Назначение ролей сверять
   с реализацией компонентов; избегать пересекающихся и слишком широких рекомендаций.
9. Разделять связанные понятия: типографическую роль и цвет, внешний вид
   заголовка и HTML-уровень, плотность и размер текста, наведение и выбор.
   Смежную тему кратко пояснять и давать ссылку на её страницу.
10. Перед кодом указывать его назначение: использование компонента или
    собственные стили. Код должен соответствовать показанному результату
    и не подразумевать несуществующее автоматическое поведение.
11. Использовать общее оглавление: справа на широком экране, раскрываемое
    на узком; понятные заголовки и прямые ссылки. Проверять четыре режима
    из раздела «Команды и разработка», ширину 390 px и широкий экран,
    клавиатуру, доступность и навигацию по разделам.

Критерий понятности: после начала страницы человек понимает, что уже делает
система, что нужно выбрать ему и куда обратиться за подробностями.

## Релиз

- Ветки: `master` (релизы), `develop`, фичи `feature/*` от develop. Коммиты на английском.
- Версия в `package.json` — разрабатываемая. Релиз — `/aurora-release`: CHANGELOG
  `## [Unreleased]` → `## [X.Y.Z] — YYYY-MM-DD`, fast-forward master, затем develop
  переводится на следующую версию (`npm version <next> --no-git-tag-version`)
  с новым `## [Unreleased]`. Push делает человек.
- Перед релизом: чистый `develop`, fetch origin, нет отставания от origin/develop,
  origin/master — предок develop; версия согласована с package-lock.json, тег версии
  отсутствует локально и на origin, `mise exec -- npm run verify` проходит полностью.
- Коммиты: `chore: release X.Y.Z` закрывает CHANGELOG; после fast-forward master
  `chore: start <next>` меняет package.json, package-lock.json и открывает `[Unreleased]`.
  Версию повышать после релиза; legacy-исключение описано в docs/release.md.
- Перед передачей ручного push показать выпускаемую и следующую версии, release notes,
  состав коммитов и результат проверок. Не обходить защиту веток, не применять force
  или merge-коммит вместо fast-forward. Подготовка стандарта не означает запуск релиза.
- Push в master публикует пакет, ставит тег `v<version>` и GitHub Release через
  `.github/workflows/ci.yml`. Агент не выполняет `npm publish`, релизный `git push`,
  `git tag v*` или `npm version` с созданием тега.
- Версии и порядок выпуска — [docs/release.md](docs/release.md); ломающее изменение → MAJOR.
- `tools/guard-command.mjs` проверяет команды без выполнения payload. Codex подключает
  его через `.codex/hooks.json`; пользователь подтверждает доверие через `/hooks`.
  Проверка CLI не доказывает активацию в хосте. До подтверждения старый Claude-хук сохраняется.
