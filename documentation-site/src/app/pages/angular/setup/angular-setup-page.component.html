Для разработки UI kit используется Angular 19.2.25 и TypeScript 5.8.3. Проверенные потребители — Angular 19.2.25 и 20.3.34 с Zone.js. Peer range — ^19.2.25 || >=20.3.34; более новые major не проверены. SSR, hydration и zoneless пока не проверены. Node 22.12+ (в проекте 22.23.2), доступ к GitHub. Для графиков — ECharts 6.1+; ECharts 5 не поддерживается. Правила компонентов и критерии совместимости описаны в правилах UI kit .

1. Доступ к пакету

Репозиторий PrimaSoftLLC/aurora-web-design-system публичный: для чтения исходников отдельный доступ не нужен. Пакет @primasoftllc/design-system распространяется через GitHub Packages.

Для установки npm-пакетов GitHub Packages требует авторизацию даже при публичной видимости пакета. Публичность исходников и права на пакет — разные настройки; подробнее — документация GitHub Packages .

  1. Создайте PAT classic со scope read:packages (GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic)). Fine-grained токен GitHub Packages не принимает.
  2. Положите токен в переменную окружения NODE_AUTH_TOKEN (в профиль оболочки, не в репозиторий).

9. Как писать стили

  • Цвет — только var(--ds-*). Размеры — только px, без rem.
  • Свой :focus, рамку текстового поля и box-shadow не рисовать: кольцо фокуса и рамка уже в системе.
  • Шрифт — ролью: font: var(--ds-type-body).
  • Литералы цветов в TypeScript (конфиги ECharts) линтер не видит — берите dsEChartsTheme из @primasoftllc/design-system/echarts-theme и перестраивайте график при смене скоупа ( auroraWatchScopes, графики ).

Что проверяет линтер

Правило Что ловит
aurora/known-token var(--ds-…) на несуществующий токен; объявление своих --ds-*
aurora/no-literal-color hex, rgb(), hsl(), oklch(), именованные цвета
aurora/no-rem rem вместо px

Версия правил совпадает с версией токенов: линтер поставляется в том же пакете. Правила и опции — справочник линтера . В новом приложении включайте его сразу, в существующем — на срезе 1, после перевода цветов на токены.

Ограничения

Литералы в TypeScript (конфиги ECharts — главный канал, через который цвета просачиваются мимо SCSS), inline [style] в шаблонах Angular, глубокие импорты внутренностей пакета. Это ESLint-слой, его пока нет.

И он ничего не знает про роль токена: color: var(--ds-surface) — формально валидно, содержательно ошибка. Это видит только ревьюер, и ради этого приёмка по-прежнему существует.

Приёмка экрана

Шесть пунктов. Формулировки проверяемые — «выглядит как система» критерием не является.

  1. Ни одного литерального цвета вне токенов — ни в SCSS, ни в шаблоне, ни в TS.
  2. Размеры в px. rem в новом коде нет (порталы ставят html { font-size: 10px } ).
  3. Собственных :focus и рамок полей нет — фокус и поле приходят из общего dist/styles.css пакета.
  4. Тени — только ступенями системы ( var(--ds-shadow-*) ), своих box-shadow нет.
  5. Экран отрисован в четырёх режимах и в каждом читается: DEFAULT/light/cozy, DEFAULT/dark/compact, RED2/light/cozy, RED2/dark/compact.
  6. У каждой кнопки, которая шлёт запрос, есть состояние загрузки; AXE чистый; :focus-visible проверен с клавиатуры, а не в devtools.

Передача на ревью

Заявка на приёмку — это ссылка на PR плюс четыре скриншота экрана в четырёх режимах. Без скриншотов заявка не рассматривается: их отсутствие почти всегда означает, что в тёмной теме экран не открывали.

Владелец смотрит: соответствие спецификации компонента, выбор токена по роли (не по цвету), поведение в compact и в dark, пустое состояние и состояние загрузки.

CSS-нарушения должны быть исправлены до ревью. Литералы в TS, inline-стили и глубокие импорты текущий stylelint не проверяет — их нужно смотреть отдельно.

Предметом приёмки не является вёрстка бизнес-логики, тексты и раскладка полей — система задаёт внешний вид, а не структуру экрана.

Ответственность

Подтверждённый первый потребитель пакета — aur-billing. Состояние пилотов и готовность каждого приложения фиксируются в его задачах; этот документ не объявляет внедрение завершённым. Найденные пробелы оформляются в репозитории системы. Экран принимает владелец системы или назначенный ревьюер команды.

Пилот

Пилот существует не чтобы «первое приложение выглядело хорошо», а чтобы вскрыть дыры в системе до того, как в неё упрутся команды с легаси. Пилот обязан ответить на список вопросов и закрыть каждый задачей в репозитории системы:

  • каких токенов не хватило и в каких ролях;
  • какие компоненты пришлось писать с нуля, потому что в системе нет спецификации;
  • где спецификация есть, но она не покрывает реальное состояние (ошибка, загрузка, пусто, очень длинный текст, очень много колонок);
  • что ломается в compact, что — в dark;
  • что происходит с графиками при смене скоупа;
  • что пришлось сделать вопреки правилам и почему.

Пока пилот идёт, каждое «сделаю пока по-своему» фиксируется как // TODO: DS-<id> со ссылкой на задачу. Список этих TODO — и есть отчёт пилота.

Пилот закрыт, когда: все экраны приняты, список TODO пуст или сознательно отложен владельцем, и правки, которые пилот породил, выпущены версией системы. До этого момента существующие приложения не подключаются — иначе они получат систему, которую придётся ломать мажором через месяц.

Существующее приложение

Главное правило: срез делается по всему приложению целиком, а не экран за экраном. «Три экрана полностью на системе, остальные как были» выглядит хуже, чем приложение, которое вообще её не подключало, и команда быстро теряет к затее интерес.

Порядок срезов — по возрастанию визуального риска:

Срез 0 — подключение. Пакет ставится, стили подключаются, но ничего своего не удаляется. Вид приложения не меняется. Если меняется — значит есть конфликт глобальных селекторов, и до его разбора дальше идти нельзя: скоуп вешается на контейнер вместо <body>, пока легаси не вычищено.

Срез 1 — цвета. Литеральные цвета заменяются семантическими токенами по назначению: текст, поверхность, граница, статус. Вид не меняется, дифф механический, делается массово и ревьюится быстро. Здесь же включается линтер системы — с этого момента новые литералы в проект не попадают.

Срез 2 — типографика и плотность. Вид меняется. Делается экраном за экраном и согласуется до начала работ, а не после.

Срез 3 — компоненты. По одному, в порядке частоты: кнопка, поле, таблица, диалог, дальше по месту. Каждый компонент — отдельный PR по всему приложению.

Срез 4 — уборка. Собственные :focus, тени, рамки, дубли переменных. Делается последним, когда токены уже везде: раньше это просто сломает вид.

Не переписывается: бизнес-логика, структура экранов, роутинг. Если срез тянет за собой рефакторинг логики — срез разбит неправильно.

Когда токена или компонента не хватает

Локальный #3A7BD5 «на время» — главный способ убить систему, и он всегда появляется под дедлайном. Поэтому путь должен быть короче обхода:

  1. Задача в репозиторий системы: что за роль, где именно, скриншот.
  2. Сегодня, пока токена нет: ближайший подходящий токен по роли плюс // TODO: DS-<id>. Литерал не коммитится никогда.
  3. Согласуйте срок ответа с владельцем в задаче. Общий SLA пока не установлен.

Отдельно: запрос «нам нужен свой цвет» почти всегда означает «нам нужна роль, которой нет в системе». Обсуждается роль, а не hex.

Антипаттерны

  • Скопировать tokens.css к себе и «немного поправить».
  • Форкнуть пакет под нужды одного приложения.
  • Обернуть компонент системы в свою обёртку, которая переопределяет его стили.
  • Принять экран, не открыв его в dark и compact.
  • Переводить приложение без выбранного среза, критериев приёмки и задач на выявленные пробелы.
  • Держать в приложении свой набор переменных, который «мапится» на токены.

Обновление системы

npm i -E @primasoftllc/design-system@X.Y.Z отдельным коммитом. MAJOR — ломающие изменения: прочитайте раздел версии в CHANGELOG.md, правки кода — в том же коммите. Patch и minor не должны ломать приложение; major планируется отдельной задачей. Приложение не остаётся на старом мажоре дольше одного релизного цикла системы. Критерии выбора версии — политика версий .
