# Сайт документации Aurora

Отдельное Angular-приложение, которое постепенно заменит существующий сайт.
Добавлены общая оболочка, отдельные меню дизайн-системы и компонентов, поиск
по названиям и группам меню, настройки демонстраций. По образцу старого сайта перенесены
22 страницы основ дизайн-системы, включая справочник токенов, и три страницы инструкций:
«Подключение Angular», «Добавление компонентов», «Брейкпоинты: решения по миграции». Часть интерактивных демонстраций остаётся заглушками
до подготовки необходимых Angular-компонентов.
React-пример поиска на вводной странице заменён заглушкой до подготовки
Angular-компонентов. Исходники старого сайта сохраняются без изменений.
На время перехода тексты перенесённых страниц допустимо хранить в обеих версиях.
Авторские Angular-шаблоны находятся в `src/app/pages/`; старые копии будут удалены
вместе с прежним сайтом. Отдельной системы синхронизации текстов не вводится.
Оглавление обычных статей формируется по `h2[id]` и `h3[id]` внутри статьи автоматически:
заголовок и стабильный `id` задаются только в шаблоне, отдельного списка нет.
Текущий раздел подсвечивается при прокрутке и переходах по якорям. Обычная
прокрутка не меняет адрес страницы и историю браузера.

В каталоге доступны Icon, Button, FAB и Checkbox: соответственно пять, восемь,
пять и семь сценариев, код, правила, параметры и токены. Checkbox расположен
в группе «Поля и выбор», остальные — в «Кнопки и иконки». Это не окончательный
состав библиотеки. Точечные проверки компонентов прошли 2026-10-30;
полный verify текущего этапа не запускался.
Настройки в шапке пока используют нативные select; замена их общими компонентами
и сравнение четырёх режимов остаются последующими этапами.

Зависимости и команды находятся в корневом `package.json`.
Все команды выполняются из корня репозитория:

```sh
npm install
npm run dev:site-angular
npm run build:site-angular
```

Разработка: <http://127.0.0.1:4200/>. Angular CLI отслеживает изменения
исходников сайта и обновляет приложение в браузере. Перед запуском автоматически
собираются дизайн-система и Angular UI-kit; в dev-режиме изменения их исходников
также вызывают пересборку и обновление сайта. Ошибки выводятся в терминал;
после исправления исходника наблюдение продолжает работать.
Учитываются также отдельные HTML-шаблоны и SCSS-файлы библиотеки. Изменения
настроек сборщика требуют перезапуска команды; специальные проверки удаления,
переименования ресурсов и аварийного завершения процессов пока не добавлены.

## Страницы и оформление исходников

Каждая перенесённая статья и страница компонента имеет собственный route-компонент.
Примеры расположения:

- `src/app/pages/foundations/overview/` — вводная страница;
- `src/app/pages/foundations/typography/` — типографика;
- `src/app/pages/foundations/colors/` — нейтральные цвета, образцы и расчёт контраста;
- `src/app/pages/foundations/shape/` — форма, глубина, шкалы радиусов и теней;
- `src/app/pages/foundations/theme-colors/` — подбор палитры и чистая функция расчёта;
- `src/app/pages/tokens/` — поведение генерируемого справочника токенов;
- `src/app/pages/components/index/` — начальная страница каталога;
- `src/app/pages/components/icon/` и `button/` — отдельные страницы компонентов.

Маршруты перечислены в `src/app/app.routes.ts`. Содержимое страниц не выбирается
общим `switch` или параметром `data`. Новая статья добавляется своим компонентом
и маршрутом. Вложенные адреса также можно добавлять отдельными маршрутами.
Все пункты меню дизайн-системы имеют явные маршруты. Временный генератор
маршрутов к пустым страницам удалён; для неизвестных адресов остаётся отдельная
страница 404. Проверка сайта сверяет меню с явными маршрутами.

`shared/article-layout/` — общая оболочка статьи: заголовок, проекция содержимого,
автоматическое оглавление и подсветка текущего раздела. Она не импортирует конкретные
страницы и не выбирает их содержимое.

`shared/heading-anchor/` добавляет ссылки у заголовков через директиву
`auroraHeadingAnchors` на общей области main. Поэтому ссылки есть как в статьях
с ArticleLayout, так и в отдельных документах без оглавления. Внутренний
HeadingAnchorComponent использует DsIcon и RouterLink; в публичную библиотеку
он не экспортируется.

Шаблоны и стили страниц хранятся в отдельных `.html` и `.scss` рядом с `.ts`.
Inline-вариант допустим только для действительно небольшого шаблона или стилей.
SCSS обрабатывает уже установленный Angular-сборщик; стили дизайн-системы остаются
готовым CSS, а сборка самой библиотеки UI-kit этим изменением не переводится на SCSS.
Системные CSS-переменные сохраняются; SCSS не создаёт вторую систему токенов.

Форматирование: два пробела, ориентир 100 символов, переносимые строки не длиннее
120. Правила заданы в локальных `.prettierrc.json` и `.editorconfig`:

```sh
npm run format:site
npm run format:site:check
```

Форматтер работает только в `documentation-site/`; генерируемые файлы игнорируются.
Команды используют Prettier с дополнительными правилами для HTML:
первый атрибут остаётся на строке открывающего тега. Закрывающий `>` остаётся
рядом с последним атрибутом; знаки пунктуации после inline-тегов не отделяются
добавленным пробелом или переносом. Для сохранения этих правил используется
`tools/format.mjs`, а не прямой запуск Prettier.
Проверка форматирования также включена в `verify`, группу `catalogue`.
Используются явные закрывающие теги Angular-компонентов, чтобы не провоцировать
HTML-инспекции IDE, хотя Angular поддерживает самозакрывающуюся запись.
В `tsconfig.json` включены строгая проверка шаблонов, неиспользуемых переменных,
параметров и импортов в `imports` компонентов. Эти ошибки останавливают сборку сайта.

Повторяющиеся стили статей находятся в `src/styles/_article.scss`.
Базовые SCSS-mixins подключаются в прежней позиции каскада через `@use` / `@include`;
они не добавляют глобальные правила. Обычная и более простая типографика,
таблицы и раскрывающиеся разделы сохраняют свои варианты оформления.
Заголовки, ссылки, вводные абзацы, подписи и код в тексте также используют общие
mixins. Параметры сохраняют существующие отличия, например отступ заголовка
12 или 16 px, цвет подзаголовка и перенос кода. Это общие правила оформления
документации, а не дополнительная система дизайн-токенов.
Списки ссылок раздела «Дальше» оформляет общий mixin `related-links`, подключённый
в `src/styles.scss`: одинаковые маркеры и отступы, без дополнительного промежутка
между пунктами. Правило ограничено этим разделом и не меняет остальные списки.

Данные словаря иконок, шкал, палитр и примера скоростей находятся в
`src/app/data/`. Это readonly-данные для отображения через `@for`,
а не ограничение публичного API компонентов. Значения CSS-токенов по-прежнему
задаются дизайн-системой. Тексты разделов и расположение блоков остаются на страницах.

## Общие блоки содержимого

Три независимых компонента сайта находятся в `src/app/shared/` и не входят в UI-kit:

- `ExampleBlockComponent` (`aurora-example-block`) — проекция содержимого,
  рамка `--ds-border`, радиус `--ds-radius-lg`, внутренний отступ 24 px
  (16 px при ширине до 400 px). `background="surface"` использует `--ds-surface`,
  `background="subtle"` — `--ds-bg`. Цвет текста — `--ds-fg`.
  Внешние отступы и настройки темы задаёт родитель.
- `CodeBlockComponent` (`aurora-code-block`) — обязательный объект `snippet` типа
  `CodeSnippet`: строка `code`, язык `language`
  (typescript/html/css/scss/json/yaml/shell/text), необязательный `fileName`.
  По умолчанию код виден; `collapsible` добавляет собственное раскрытие
  «Показать код» / «Скрыть код». Компонент сам копирует исходную строку;
  при отказе clipboard выделяет код для ручного копирования.
- `DisclosureComponent` (`aurora-disclosure`) — нативные details/summary,
  закрытые по умолчанию. Заголовок проецируется через `slot="title"`, остальное
  содержимое — в тело. Этот компонент не используется внутри CodeBlock.

Отступы кода сохраняются через `pre` и `white-space: pre`, длинные строки
прокручиваются внутри блока. Подсветка использует уже установленный highlight.js,
как в старом каталоге, с ограниченным набором языков. Цвета подсветки взяты
из прежних общих стилей и используют токены. Angular дополнительно очищает
сгенерированный HTML; исходный код не вставляется в шаблон как исполняемая разметка.
Файл `_code-highlighting.scss` ограничивает правила вставленных span-элементов
селектором `aurora-code-block`.

Первое применение — обёртка и два варианта кода на странице Icon, раскрывашка
полного названия в «Типографике». Открытый HTML и раскрываемый TypeScript на
странице Icon временно показывают оба режима общего блока, а не задают окончательную
структуру страницы компонента. Цвет подписи Disclosure соответствует этому месту
«Типографики»; для других статей оформление нужно сверять с оригиналом, а не
автоматически применять синий цвет всюду. Исходники передаются со страниц
типизированными сниппетами; организация полноценных работающих демонстраций
обсуждается отдельно.

В «Нейтральных цветах» и «Форме и глубине» сохранены исходные разделы,
статические образцы, справочники и связанные темы из preview и README старого сайта.
Расчёт контраста использует вычисленные CSS-цвета выбранного оформления.
Демонстрации, которым нужны ещё не готовые Angular-компоненты, и соответствующий
React-код заменены явными заглушками. Обычный CSS-пример контейнера перенесён.
Нативные details этих статей сохраняют собственное оформление старых страниц,
без автоматической замены на синий вариант Disclosure.

## Локальные результаты и публичные импорты

Обе команды сначала используют существующие сборщики библиотеки, затем Angular CLI.
Старый каталог и React при этом не собираются. Отдельная подготовка доступна
командами `npm run build:design-system` и `npm run build:ui-kit-angular`.

- CSS, токены и JSON: корневой `dist/`.
- Шрифты: корневые `fonts/` и `assets/fonts/`, как в публикуемом пакете.
- Angular-библиотека: `dist/angular/` (partial compilation и типы).

Это генерируемые, игнорируемые Git файлы. Исходники редактируются только
в `design-system/` и `ng-ui-kit/src/`, исходники сайта — в `documentation-site/src/`.
Очистку выходных папок во время
работы dev-сервера выполнять не следует.

Компоненты импортируются из `@primasoftllc/design-system/angular`, CSS —
из `@primasoftllc/design-system/styles.css`. Поскольку сайт находится внутри
пакета с этим именем, импорты разрешаются через корневой `package.json` и его
`exports` в локальный `dist/`. Нет установки пакета в себя, source aliases
или разных путей для dev и production. Angular CLI связывает partial-код
библиотеки и переносит файлы шрифтов из CSS в результат сборки сайта.

В dev-режиме предварительное кеширование Angular-входа отключено, чтобы сервер
видел новую сборку библиотеки. Изменения исходников объединяются перед сборкой;
пересборки зависимостей выполняются последовательно.

Главная: `/`; темы: `/foundations/typography` и другие адреса из
`src/app/navigation.ts`; каталог: `/components`; компонент: `/components/icon`.
Разделы статьи открываются обычными якорями, например
`/foundations/typography#fonts`. Query-параметры `theme`, `appearance`, `density`
сохраняют настройки демонстраций в ссылке. Документация остаётся DEFAULT/light/cozy.
Повторный клик по тому же якорю также прокручивает к разделу, даже если URL
не изменился.

У каждого h2[id] и h3[id] внутри article есть значок ссылки. На компьютере
он виден при наведении на заголовок или фокусе внутри него; на устройствах без
наведения — постоянно. Место под ссылку сохраняется, чтобы текст не сдвигался.
Доступное имя: «Ссылка на раздел „Название“». У h1 значка нет.
Ссылка сохраняет текущий путь, query-параметры и использует существующий id
в качестве fragment; заголовки без id автоматически не переименовываются.
Работают обычный переход, новая вкладка и копирование адреса через меню браузера.
Автоматического копирования по нажатию нет.

При смене страницы, текста или id ссылки обновляются; динамические компоненты,
подписка маршрутизатора и наблюдатель DOM освобождаются при удалении.
Значок исключается из названия раздела в оглавлении и из доступного имени
собственной ссылки. Последние изменения пока не проверены сборкой или тестами.

Структура меню определяется полями `id`, `section` и `level`
в `navigation.ts`, а не сравнением видимых русских названий.
Все страницы подключены без ленивой загрузки. Dev-сервер поддерживает
прямое открытие маршрутов. При размещении production-сборки сервер должен
возвращать `index.html` для маршрутов приложения. Для размещения в подпапке
нужно задать её путь через `--base-href` при сборке. Настройка нового сайта
для GitHub Pages будет выполнена на этапе переключения публикации.
GitHub Pages сам по себе не предоставляет универсальный SPA fallback.
Проверка сайта в подпапке не означает, что прямые ссылки на Pages уже настроены.

Production-сборка: `documentation-site/dist/browser/`. Для просмотра её
нужно раздавать HTTP-сервером; открытие `index.html` через `file://` не предусмотрено.
Результат расположен вне корневого `dist/`, чтобы существующая упаковка
библиотеки не включала сайт. Папка `dist/` уже исключена из Git.

Существующие `npm run dev`, `npm run build`, сборка пакета и GitHub Pages
пока используют прежнюю реализацию. Новые команды не запускают эти сборки.

## Проверка нового сайта

`npm run verify` включает форматирование, сборку и браузерную проверку нового сайта.
В CI они выполняются в существующей группе `catalogue`, после проверок старого
каталога. Отдельно эти шаги можно запустить из корня:

```sh
npm run format:site:check
node documentation-site/tools/run.mjs build --base-href /site-check/ --output-path ../.tmp/documentation-site-check
node documentation-site/tests/smoke.mjs
```

Браузерные проверки разделены по ответственности:

- `tests/articles.mjs` — содержание статей, режимы и примеры;
- `tests/guides.mjs` — инструкции Angular и решения по миграции: текст, код, ссылки и адаптивность;
- `tests/accessibility.mjs` — общая проверка доступности с узким исключением для временных отметок;
- `tests/tokens.mjs` — справочник токенов, фильтры и копирование;
- `tests/shell.mjs` — оболочка, оглавление и страницы компонентов;
- `tests/fixture.mjs` — общий сервер и браузер с единым закрытием ресурсов.

Без аргументов `smoke.mjs` выполняет все группы, как и раньше. После сборки
можно запустить только нужные проверки, не меняя тестовые файлы:

```sh
node documentation-site/tests/smoke.mjs shell tokens
node documentation-site/tests/smoke.mjs articles --pages=colors,shape,iconography,status,charts,themes
```

Нужен Chromium из Playwright (`npx playwright install chromium`). Для локальной
проверки установленным Chrome можно задать `PLAYWRIGHT_CHANNEL=chrome`
(в PowerShell: `$env:PLAYWRIGHT_CHANNEL = 'chrome'`). По умолчанию CI использует
Chromium. Проверка запускает временный HTTP-сервер и закрывает его по завершении.

Проверяются загрузка ресурсов из подпапки, прямые маршруты и якоря, публичная
иконка и шрифт, четыре режима, автоматическое оглавление, поиск, мобильное меню
и доступность. Сервер проверки эмулирует SPA fallback, а не правила GitHub Pages.
Настройки сайта и общие блоки проверяются через пользовательские сценарии в браузере;
отдельного набора Angular unit-тестов для каждого компонента или сервиса пока нет.
Эти проверки не заменяют визуальную сверку со старым сайтом, проверку dev-наблюдения
или установку опубликованного пакета в независимый проект.

## Справочник токенов

Страница `/tokens` генерируется перед запуском и сборкой из
`design-system/tokens/source.json` через существующие `readTokenModel` и
`renderTokenReference`. Скрипт `tools/build-token-page.mjs` внутри сайта создаёт
Angular-шаблон и поисковые метаданные в игнорируемой папке `.tmp/` сайта.
Генерируемые файлы вручную не редактируются. При изменении канонической
разметки генератор проверяет, что каждому токену, разделу и элементам управления
по-прежнему назначены Angular-привязки; несоответствие останавливает сборку. В браузере работают Angular-привязки
и `TokensPageComponent`, старый `token-reference.js` не подключается.

`dev:site-angular` и `build:site-angular` подготавливают страницу автоматически;
изменение исходных токенов в dev-режиме обновляет её вместе со стилями.
При прямом запуске Angular CLI сначала выполните
`node documentation-site/tools/build-token-page.mjs` из корня репозитория.

Сохранены группы, поиск по всем группам, категории, выбор бренда, ссылки на токены,
копирование CSS-переменной и демонстрация длительностей с учётом уменьшения движения.
Настройки фильтра сохраняются в URL. Образцы примитивов могут намеренно показывать
низкоконтрастный цвет: автоматическая проверка доступности страницы исключает
только `.token-sample`, сохраняя проверку элементов управления и текста справочника.

Чистый расчёт палитры проверяется отдельно, без браузера:

```sh
node documentation-site/tests/palette-calculator.mjs
```

Тест также запускается из браузерного smoke перед проверкой интерфейса.
На время миграции он сравнивает пять пар цветов с исходным калькулятором,
включая светлые, тёмные и близкие к статусам цвета. При удалении старого
калькулятора эту проверку потребуется перевести на зафиксированные эталоны.

## Кодовые фрагменты

Статические сниппеты хранятся рядом со страницей в `*-page.snippets.ts`.
Один именованный объект страницы объявляется через `satisfies Record<string, CodeSnippet>`.
Компонент импортирует его как `protected readonly snippets = pageSnippets`, без
расширения типа до `Record<string, CodeSnippet>`: так сохраняется проверка имён
в Angular-шаблонах. В блок передаётся `[snippet]="snippets.example"`;
`collapsible` остаётся отдельной настройкой отображения.

Тип и список языков находятся в `shared/code-block/code-snippet.ts`. Текст
сниппетов остаётся данными и не компилируется как Angular-компонент. Страницы
без готового кода пока не получают пустых файлов. Рассчитываемый CSS палитры
передаётся через `computed<CodeSnippet>`: это динамический результат калькулятора.
Новый сайт документирует Angular API. Перечни старых компонентов и инструкции React
из страниц удалены. Состав и API библиотеки согласуются отдельно; подписи заглушек
описывают недостающие демонстрации, а не перечень обещанных экспортов.
