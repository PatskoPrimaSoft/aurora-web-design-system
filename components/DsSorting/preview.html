A · В таблице: порядок задаёт заголовок

Заголовок столбца делает одно дело — сортирует. Фильтрация ушла в DsFilterBar и DsFilterMenu (в v1 фильтр сидел внутри ячейки заголовка и делал шапку двухэтажной). Кликните по заголовкам: под таблицей видно, что именно уходит на сервер.

B · Три состояния заголовка, но цикл из двух

цикл

Клик по неактивному заголовку → возрастание. Клик по активному → убывание. Ещё клик → снова возрастание. Состояния «не отсортировано» в цикле нет: дефолтный порядок — тоже сортировка (-createdTime, -name), и «сброс» вернул бы третий порядок, которого никто не просил.

Два столбца одновременно не сортируются никогда. Мультисортировка (shift-клик, приоритеты) в системе отсутствует: серверный контракт принимает один ключ — sort=desc#name.

Заголовок сортируемого столбца — настоящая <button> внутри <th>: сортировка это действие, значит доступна с клавиатуры и получает кольцо :focus-visible. На <th> при этом стоит aria-sort: ascending / descending у активного и none у остальных сортируемых.

C · Какой столбец делать сортируемым

Критерий один: порядок должен уметь считать тот, кто отдаёт строки. Таблицы админ-портала листаются на сервере, поэтому «клиентская» сортировка переупорядочила бы только текущую страницу из 148 строк — это не сортировка, а ложь. Нет серверного поля — нет иконки в заголовке.

Столбец из примера вышеСортируемыйПочему
nameдапростое поле, sort=asc#name
groupдапростое поле связанной сущности
driverдаячейка составная («И. Иванов»), поэтому у столбца объявлен sortBy: 'driver.lastName' — подпись столбца при этом не меняется
speed · lastдателеметрия в mono-столбце; числа и время — самые частые сортировки на экране
stateдапо шкале серьёзности, не по алфавиту: alarm → нет данных → движется → стоит → offline. Шкала объявлена рядом со статусной палитрой — иначе «Alarm» встанет между «Offline» и «Parked» и переедет при переводе
mileageнетсчитается в браузере по треку: сервер такого поля не знает
— выбор, действиянетслужебные столбцы: чекбокс и колонка действий не сортируют никогда
  • Пустое значение — всегда самый низ шкалы, независимо от направления: строки с «—» собираются на слабом конце (по возрастанию — сверху, по убыванию — снизу). Оператор ищет «у кого хуже всего», и пустое не должно притворяться нулём в середине.
  • Смена порядка возвращает на первую страницу. Иначе оператор остаётся на 4-й странице нового порядка и видит середину выборки. Размер страницы при этом сохраняется (он живёт в localStorage).
  • Порядок таблицы живёт в URL (?sort=-name) вместе с фильтрами и страницей: ссылка на «объекты, отсортированные по последнему сообщению» должна открываться у коллеги такой же.
  • Во время перезапроса строки не исчезают. Старые строки остаются на месте, поверх — DsSkeleton; спиннер на месте таблицы стирает контекст, ради которого оператор и нажал заголовок.
Компоненты: DsTable — sortKey, sortDir, onSort(key, dir), колонка с sortable и при необходимости sortBy.
